# DECISIONS.md - Описание индивидуального варианта

## 1. Номер варианта
Вариант: 24

## 2. Часть А. Изменённое правило
Правило: R2, R3, R4 (добавление обязательного поля `tags`)

Что было: Карточка клиента (`Client` и `ClientDraft`) содержала только 3 обязательных поля (`inn`, `name`, `email`), а парсер и валидатор проверяли только формат этих трёх полей.

Что стало: В `Client` и `ClientDraft` добавлено четвёртое обязательное поле `tags`. Парсер `ClientCsvParser` требует ровно 4 поля в строке CSV, а `ClientValidator` проверяет, что `tags` не пустое и содержит от 1 до 5 непустых тегов, разделённых запятой.

Почему: Добавление тегов позволяет сегментировать клиентов при импорте в CRM и отсеивать некорректные или перегруженные списки тегов до сохранения записи в базу.

## 3. Часть Б. Новый метод
Класс: `ImportResult`
Метод: `addTagCount`
Сигнатура: `public static int addTagCount(ImportResult r)`
Назначение: Подсчитывает и возвращает суммарное количество тегов во всех успешно импортированных карточках клиентов.

Код метода:
```java
public static int addTagCount(ImportResult r) {
    int totalTags = 0;
    for (Client c : r.acceptedClients()) {
        if (c.tags() != null && !c.tags().isBlank()) {
            String[] parts = c.tags().split(",");
            totalTags += parts.length;
        }
    }
    return totalTags;
}
```

## 4. Ответы на контрольные вопросы (50-150 слов каждый)

Вопрос 1: Наиболее вероятной ошибкой входных данных при пакетном импорте является опечатка в ИНН (неверная длина или случайные буквы) либо отсутствие символа `@` в поле email. От этих ошибок защищают проверки правил R3 и R4 в методе `ClientValidator.validate(ClientDraft)`. Поскольку CSV-файлы часто заполняются вручную или выгружаются из устаревших таблиц, ошибки в идентификаторах и почте встречаются чаще всего. Размещение проверок в отдельном классе-валидаторе позволяет отсеять бракованные записи до их сохранения в `ClientRepository`.

Вопрос 2: Ключевое бизнес-правило устойчивого пакетного импорта (R6 — продолжение импорта при ошибке отдельной строки) размещено в методе `ClientImporter.importFile(Path)` в виде блока `try-catch` внутри цикла чтения строк. Такое размещение обусловлено принципом разделения ответственности (SRP): `ClientParser` и `ClientValidator` отвечают только за диагностику проблем конкретной строки и выброс исключения, а координатор `ClientImporter` перехватывает его, фиксирует номер строки в `ImportResult` и переходит к следующей записи.

Вопрос 3: Узел `n5` («Разобрать строку (4 поля) и проверить ИНН, email, tags (1..5)») и ромб `n6` («Строка корректна и ИНН уникален?») на Activity-диаграмме напрямую отражают тело цикла `while` в методе `ClientImporter.importFile`. Узел `n5` соответствует последовательным вызовам `parser.parse(line, lineNumber)` и `validator.validate(draft)`. Если проверка проходит успешно (`n6` -> «да»), выполняется узел `n7` (`repository.save`), а если возникает ошибка (`n6` -> «нет»), управление переходит в узел `n8` (`result.addError`) и по обратной стрелке возвращается к чтению следующей строки.

Вопрос 4: Изменение требований к формату существующих полей (например, изменение допустимой длины ИНН с 10/12 цифр на 13 цифр или изменение лимита количества тегов с 5 на 10) затронет только один класс — `ClientValidator`. Это связано с тем, что вся логика проверки бизнес-правил локализована исключительно в методе `validate`. Классы `ClientCsvParser`, `ClientImporter`, `ClientRepository` и `ImportResult` не зависят от правил валидации полей и не потребуют никаких правок.

## 5. Фрагмент кода для анализа
Фрагмент:
```java
// Антипаттерн - общий catch для всего цикла, останавливает импорт при первой ошибке
try {
    for (String line : lines) importLine(line);
} catch (Exception e) {
    return; // первая плохая строка останавливает весь импорт
}
```
Проблема: Общий блок `try-catch` охватывает весь цикл обработки строк, из-за чего первое же исключение при разборе или валидации прерывает выполнение метода. В результате все последующие строки файла (включая корректные) не обрабатываются, а информация о номере проблемной строки теряется, что напрямую нарушает правила R5 (локализация ошибки) и R6 (продолжение импорта).

Исправление:
```java
for (int i = 0; i < lines.size(); i++) {
    try {
        importLine(lines.get(i), i + 1);
    } catch (Exception e) {
        result.addError(new ImportError(i + 1, e.getMessage()));
    }
}
```
