# DECISIONS.md

## Вариант
Номер варианта: 24

Часть А: R6 — стоимость за км = `60` (вместо `50`) в методе `StandardCourierPolicy.calculateCost`. Формула изменена на `Math.max(500.0, req.distanceKm() * 60.0)`. Благодаря инкапсуляции формулы внутри политики изменения не затронули сервис и фабрику.

Часть Б: `addCostRange(DeliveryService, DeliveryRequest) -> double` — вычисляет разброс цен (`max - min`) по всем поддерживаемым типам доставки. Метод добавлен в `DeliveryService` и использует вспомогательные методы `addMostExpensiveType` и `addCheapestCost`, которые перебирают `DeliveryType.values()` через фабрику и сравнивают стоимость только при `supports(req) == true`.

## Решение 1
**Формулировка:** Использование интерфейса `DeliveryPolicy` и отдельных классов-стратегий (`StandardCourierPolicy`, `ExpressPolicy`, `PickupPolicy`) вместо единого метода с ветвлениями `if-else`.

**Альтернатива:** Разместить все формулы расчёта и проверки веса в одном методе `DeliveryService.calculate` через цепочку `if (type == ...)`.

**Обоснование:** Паттерн Strategy изолирует формулу каждого способа доставки в отдельном классе. Это соблюдает принцип открытости/закрытости (OCP) и правило R2: при изменении тарифа (как в части А варианта) или добавлении нового способа доставки существующий код расчёта в `DeliveryService` не меняется.

## Решение 2
**Формулировка:** Выделение выбора конкретной политики в отдельный класс `DeliveryPolicyFactory` с конструкцией `switch` по `enum DeliveryType`.

**Альтернатива:** Создавать объекты политик напрямую внутри `DeliveryService` или использовать строковые константы для определения типа доставки.

**Обоснование:** Фабрика отделяет сервис от конкретных реализаций политик (правило R4 — в фабрике нет формул). Использование `enum DeliveryType` гарантирует проверку типов на этапе компиляции и полноту покрытия всех вариантов в `switch` без риска опечаток в строках.

## Ответы на контрольные вопросы

### Вопрос 1
Наибольшую гибкость при добавлении нового типа доставки обеспечивает принцип открытости/закрытости (Open/Closed Principle), реализованный через связку паттернов Strategy и Factory. За это отвечают интерфейс `DeliveryPolicy`, классы-реализации (`StandardCourierPolicy`, `ExpressPolicy`, `PickupPolicy`), фабрика `DeliveryPolicyFactory` и сервис `DeliveryService`. Чтобы добавить четвёртый тип доставки (правило R9), достаточно добавить значение в `enum DeliveryType`, создать новый класс политики и дописать одну ветку `case` в фабрику, не изменяя код сервиса и существующих политик.

### Вопрос 2
Ключевую логику выбора стратегии содержит класс `DeliveryPolicyFactory` в методе `get(DeliveryType)`. Размещение выбора именно здесь обусловлено принципом единственной ответственности (SRP) и правилом R4: фабрика отвечает исключительно за создание нужного объекта политики и не содержит формул расчёта. Благодаря этому `DeliveryService` работает только с абстрактным интерфейсом `DeliveryPolicy` и не зависит от конкретных классов, а при появлении новой стратегии изменения локализуются в одном месте.

### Вопрос 3
Узел `n3` («Получить политику через factory.get(type)») и последующее ветвление `n5` («Доставка возможна?») на Activity-диаграмме напрямую отражают код метода `DeliveryService.calculate`. Узел `n3` соответствует строке `DeliveryPolicy p = factory.get(r.type());`, где сервис получает нужную стратегию. Узел `n4` и ромб `n5` соответствуют проверке `if (!p.supports(r))`: при значении `false` поток идёт по ветке «нет» к выбросу `IllegalArgumentException`, а при `true` — к полиморфному вызову `p.calculateCost(r)`.

### Вопрос 4
Изменение тарифа или лимита веса для одного способа доставки (например, изменение стоимости за километр в стандартной доставке с 50 на 60 рублей в варианте 24) затрагивает ровно один класс — `StandardCourierPolicy`. Это происходит потому, что бизнес-правила и формулы расчёта полностью инкапсулированы внутри конкретных классов-политик. Ни `DeliveryService`, ни `DeliveryPolicyFactory`, ни остальные политики не знают о деталях этой формулы и не требуют правок.

## Фрагмент кода для анализа
В приведённом фрагменте используется условная логика `if-else` по типам доставки вместо полиморфизма, из-за чего один метод содержит все алгоритмы расчёта и нарушает принцип единственной ответственности (SRP). Главная причина проблемы — нарушение принципа открытости/закрытости (OCP): при добавлении четвёртого способа доставки придётся изменять этот метод, рискуя сломать существующие ветки. Для исправления нужно вынести каждую логику в отдельный класс, реализующий общий интерфейс `DeliveryPolicy`, выбирать реализацию через `DeliveryPolicyFactory.get(type)` и вызывать расчёт полиморфно через `policy.calculateCost(req)`. Такой подход полностью соответствует правилам R2 (полиморфный расчёт без ветвлений) и R8 (отсутствие `if-else` по типам в `DeliveryService`).
